The software stack

Every tool this book leans on, positioned in one map — what it is for, when it enters the story, and the version discipline that keeps a run reproducible

Chapter 4 promised this map. The training stack is not one tool but five layers of them, and most confusion about "what should we use" dissolves once each tool is pinned to its layer and its chapter. This appendix is the reference: the layer diagram, one table of what the book uses where, and the version discipline that Chapter 9 made non-negotiable. It is deliberately opinionated — these are the defaults this book's pipelines are built on, not a survey — and each row points back to the chapter where the choice is argued rather than asserted.

A.3Version discipline: the lockfile is part of the run

Chapter 9 established the rule for evaluation; it holds for the whole stack: a result travels with its versions or it does not travel. The failure modes are concrete — a transformers minor release changes a chat template and every eval shifts (§9.7's cliff); a flash-attn wheel built for the wrong CUDA silently falls back to a slow path and MFU drops eight points with no error; an lm-eval upgrade rewrites a task template and your GSM8K "regresses." The practice that prevents all three costs one file and one habit:

# the environment IS an artifact of the run — freeze it next to the checkpoint
pip freeze > runs/2026-09-21_7b/requirements.lock.txt
python - <<'PY' >> runs/2026-09-21_7b/env.json
import torch, json
print(json.dumps({
  "torch": torch.__version__, "cuda": torch.version.cuda,
  "cudnn": torch.backends.cudnn.version(),
  "gpu": torch.cuda.get_device_name(0),
  "nccl": ".".join(map(str, torch.cuda.nccl.version()))}))
PY
# and the habit (Ch. 9): after ANY upgrade, rerun one frozen old checkpoint
# through the suite before believing numbers from a new one.

Two containerization notes from our own runs. Build one image per project phase, not per experiment — the pre-training image (layers 1–3) and the post-training image (adds vLLM/veRL, whose CUDA-graph and NCCL expectations are the usual conflict source) want to evolve separately. And upgrade on a schedule, not on release day: the stack's top layers move monthly, and the productive rhythm is a quarterly pinned refresh with the Chapter 9 control-rerun as the gate, plus out-of-band upgrades only for a bug you are actually hitting.
